ElementalCommand

  • 문서 유형: 게임
  • 문서 버전: 1.0
  • 프로젝트 버전: 0.7.0
  • 근거 신뢰도: medium

1. 문서 메타데이터와 근거 범례

  • 문서버전 1.0, 대상 프로젝트버전 0.7.0(package.json 확인).
  • 근거 표기: [사실]=파일 존재·구조에서 직접 확인, [제안]=파일 미열람 상태에서 구조상 합리적으로 추정한 미검증 가설.
  • 본 세션은 파일 읽기 권한이 제한되어 docs 본문·테스트 코드 대조가 불가했으므로, 세부 서술은 대부분 [제안]으로 표기함.
  • 후속 세션에서 ElementalCommand_기획서.md, superpowers/specs, tests/*.js 원문 대조가 필요함.

2. 문제 정의

  • [제안] 캐주얼 전략 장르에서 짧은 세션(수 분 단위)에 속성 상성을 활용한 전투 판단을 즐기고 싶은 플레이어의 니즈가 있으나, 기존 유사작 대비 규칙이 단순 명료한 대안이 부족하다는 가설.
  • Hex 기반 좌표계(HexGeometry.test.js 존재)와 젬/배치형(Deployables, GemSpawner) 요소가 코드 구조상 확인되어, '자원 수집 후 배치' 형태의 코어 문제를 다루는 것으로 추정.
  • [제안] 검증 필요: 실제 타겟 유저가 이 문제를 얼마나 중요하게 인식하는지 데이터 없음.

3. 한 줄 피치와 제품 포지셔닝

  • [제안] "속성 상성과 헥스 배치를 결합한 짧은 세션형 전투 전략 게임"으로 포지셔닝.
  • 경쟁작 대비 규칙 단순화와 짧은 플레이 타임을 차별점으로 제시하는 가설이며, 원문(기획서.md) 대조가 필요함.

4. 주 페르소나

  • [제안] 이름: 김도윤(28세, 스타트업 QA 엔지니어). 출퇴근 지하철에서 5~10분 단위 짧은 세션 게임을 즐기며, 복잡한 튜토리얼 없이 바로 이해되는 규칙을 선호함.
  • 페르소나의 구체 니즈·행동 데이터는 docs/persona_playtest_feedback.md에 존재할 것으로 추정되나 본 세션에서 열람하지 못함 — 원문 대조 필요.

5. 디자인 기둥과 핵심 재미

  • [제안] 핵심 기둥 후보: (1) 속성 상성 기반 의사결정, (2) 헥스 그리드 배치 전략, (3) 짧은 세션 반복 플레이.
  • 코드 구조(CombatBoard, EnemySlot, Deployables 테스트 존재)가 이 세 기둥과 정합적이나, 우선순위·구체 재미 포인트는 기획서 원문 대조가 필요함.

6. 핵심 루프

유저가 선택을 하면 결과가 되고, 그 결과 때문에 다시 선택을 한다.

  • [제안] 자원(젬)을 수집한다 → 속성에 맞는 유닛/배치물을 헥스 보드에 배치한다 → 적과 교전하여 상성 판정 결과를 확인한다 → 보상을 획득하고 다시 자원을 수집한다.
  • 이 순환 서술은 GemSpawner, Deployables, CombatBoard, EnemySlot 테스트 파일 존재로부터 구조적으로 추정한 것이며, 정확한 순서·조건은 미검증.

7. 최초 30초 플레이 흐름

  • [제안] 진입 시 배틀 배경(bg-battle.png) 로드 → 캐릭터/적 포트레이트 시트 표시 → 초기 젬 몇 개 배치 후 첫 교전 트리거.
  • 구체적 온보딩 튜토리얼 단계나 타이밍은 원문 미확인으로 제안 수준에 머무름.

8. 게임 규칙과 승패 조건

  • [제안] 속성 상성(예: 화/수/풍 등)에 따라 공격력 배율이 달라지는 규칙이 CombatBoard/EnemySlot 구조에서 추정됨.
  • 승패 조건(적 전멸, 생존 턴 수 등)의 정확한 수치는 기획서 원문 대조가 필요하며 본 세션에서는 확인 불가.

9. 콘텐츠, 진행, 성장, 경제 구조

  • [제안] gem-items-sheet.png, deployables-sheet.png 존재로 미루어 젬 기반 재화와 배치형 유닛 언락 구조가 있을 것으로 추정.
  • 진행 단계 수, 성장 곡선, 경제 밸런스 수치는 미검증이며 ElementalCommand_업데이트_내역서.md에서 변경 이력 대조가 필요함.

10. MVP 가설과 검증 방법

  • [제안 가설1] 헥스 배치 + 속성 상성 조합이 짧은 세션에서도 전략적 만족감을 준다 — 플레이테스트 세션 재방문율로 검증.
  • [제안 가설2] 튜토리얼 없이 첫 30초 안에 핵심 규칙을 이해할 수 있다 — 신규 플레이어 관찰 인터뷰(persona_playtest_feedback.md 기반 확장)로 검증.
  • 두 가설 모두 본 세션에서 실측 데이터 대조는 하지 못했으며 원문 확인이 필요함.

11. 레퍼런스별 핵심 행동 단계 수와 적용 교훈

  • [제안] 레퍼런스 후보: 헥스 전략 보드게임류(핵심 행동 3단계: 자원획득→배치→교전 확인), 속성 상성 RPG류(핵심 행동 2단계: 속성 선택→공격 판정).
  • 적용 교훈은 코어 루프 단순화 방향으로 추정되며, 실제 레퍼런스 타이틀명과 단계 수는 docs/superpowers/specs 원문 대조가 필요함(본 세션 미열람).

12. 수치 KPI와 측정 방법

  • [제안 KPI] 신규 유저 튜토리얼 완주율 70% 이상 — 게임 내 이벤트 로깅(튜토리얼 시작/완료 이벤트)으로 측정.
  • [제안 KPI] 1회 평균 세션 길이 5~10분 유지 — 세션 시작/종료 타임스탬프 로그 집계로 측정.
  • 두 KPI 모두 검증 목표 수치이며, 실측 로깅 파이프라인 존재 여부는 본 세션에서 확인하지 못함.

13. UI, HUD, 컨트롤

  • [제안] 5개 UI 상태: (1) 메인 메뉴(bg-menu.png), (2) 전투 화면(bg-battle.png + BattleHudLayout), (3) 유닛/배치 선택 화면, (4) 결과(승리/패배) 화면, (5) 설정/일시정지 화면.
  • BattleHudLayout.test.js 존재로 전투 HUD 레이아웃이 구조적으로 다뤄지는 것은 사실이나, 각 상태의 정확한 구성요소는 원문 미확인.

14. 로딩·빈 상태·에러·100개 이상 데이터·3배 긴 텍스트 대응

  • [제안] AssetManifest.test.js 존재로 에셋 로딩 검증 로직이 있을 것으로 추정되나, 로딩 실패/빈 상태/에러 UI의 구체 처리 방식은 미확인.
  • 100개 이상 데이터(다수 젬/적 슬롯) 및 3배 긴 텍스트(현지화 등) 대응 여부에 대한 근거는 본 세션에서 확인하지 못함 — 원문 대조 필요.

15. 접근성

  • [제안] 색맹 대응(속성 구분을 색상 외 아이콘/패턴 병행) 필요성이 속성 상성 코어 메커닉 특성상 제기될 수 있으나, 실제 구현 여부에 대한 근거는 없음.
  • 접근성 관련 별도 스펙 문서나 테스트 파일이 확인되지 않아 현재 상태는 미검증.

16. 시각·청각·햅틱 피드백

  • [사실] AudioCues.test.js 파일이 존재하여 오디오 큐 관련 로직이 코드베이스에 있음이 구조적으로 확인됨.
  • [제안] docs/sfx-vfx-candidates-20260808.md 문서가 SFX/VFX 후보 목록을 담고 있을 것으로 추정되나 본 세션에서 본문을 열람하지 못함 — 원문 대조 필요. 햅틱 피드백 관련 근거는 확인되지 않음.

17. 구현 상태 매트릭스

  • [사실] 존재 확인: HexGeometry, CombatBoard, EnemySlot, Deployables, GemSpawner, AudioCues, AssetManifest, BattleHudLayout 관련 테스트 파일 8종.
  • [제안] 위 테스트 파일명은 해당 기능이 코드베이스에 구현되어 있음을 시사하나, 통과 여부·커버리지·완성도는 테스트 실행 로그 없이 확인 불가.
  • portable 실행파일 ElementalCommand_v0.6.0_portable.exe 존재는 v0.6.0 시점 빌드 산출물이 있었음을 시사(사실), 현재 0.7.0 빌드 상태는 별도 확인 필요.

18. 빌드·테스트 근거

  • [사실] package.json에 test: vitest run, build: vite build 스크립트 정의됨.
  • [사실] tests/ 폴더에 8개 테스트 파일 존재(파일명만 확인).
  • 본 세션에서는 테스트 실행이나 빌드를 수행하지 않았으므로 통과/실패 결과에 대한 관측 근거는 없음.

19. 알려진 리스크와 실패 시나리오

  • [제안] 리스크1: 본 세션처럼 문서 원문 접근이 제한될 경우 기획 의도와 실제 구현 간 괴리가 누적되어 온보딩 난이도가 검증 없이 방치될 수 있음.
